# Безопасность «Мой ТПУ»

Основа — документы 18, 20, 22 и `helpdesk-ai/docs/TPU_API_GUIDE.md`. Здесь они доведены до конца:
где лежит каждый секрет, как он продлевается и отзывается, кто кого и чем вызывает, что попадает в LLM.
Пометка **[сейчас]** — входит в `specs/gateway-public-mcp`; **[консоль]** — в `specs/console-and-connectors`; остальное — в спецификации identity и assistant.
Решения 19.10: паспорт вызова — да; фонового продления токенов ТПУ — нет; сроки — сайт 30 мин простоя, мобилка 7 дней, агент 30 мин;
анонимного доступа к MCP нет — только мастер-ключи доверенных клиентов. Сроки настраиваются в `application.yml`.

## 1. Что защищаем

| Класс | Примеры | Где лежит | Кто видит |
|---|---|---|---|
| Публичное | расписание, статьи help.tpu.ru, страницы сайта | кэш gateway, БД rag | все, в том числе без входа |
| Личное (ПД, 152-ФЗ) | ФИО, группа, роль, своё расписание, мои заявки, дедлайны Moodle | не храним — берём у ТПУ на время вызова; в БД только `display_name`, `roles`, `study_group` | сам пользователь; внешний агент — только после согласия на scope и по режиму выдачи (раздел 6) |
| Чувствительное | оценки, заявления, почта, медицинское | не храним | только сам пользователь на нашем сайте; наружу (MCP) не выдаётся никогда; в LLM — см. раздел 6 |
| История чата | вопросы и ответы | БД assistant | сам пользователь; срок хранения ограничен |
| Секреты | токены ТПУ, ключи api.tpu.ru, Naumen, Moodle, LLM; ключи подписи; сервисные ключи; пароли БД | раздел 3 | только тот сервис, которому секрет нужен |
| Журнал | кто, что, когда вызвал | `gateway.audit` | администратор; аргументы — только хэш |

## 2. Принципы

1. **Каждый секрет знает ровно один сервис.** Токен ТПУ видит только identity (хранит) и gateway (в памяти, на время вызова). assistant, rag, ml-server, LLM и внешний агент токенов ТПУ не видят никогда.
2. **Полномочия передаются вместе с запросом, а не «по доверию».** Сервис не может действовать от имени произвольного пользователя — только того, чей запрос он сейчас обрабатывает (раздел 5, «паспорт вызова»).
3. **Не храним того, что можно спросить у ТПУ.** Личные данные живут в кэше минуты и не пишутся в БД и логи.
4. **Модель ничего не решает в безопасности.** Права, лимиты, подтверждения, подстановка ключей — код шлюза. Модель только выбирает инструмент и пишет текст; запись — только через черновик и подтверждение человеком.
5. **Чужой токен дальше не передаётся** (требование стандарта MCP): токен внешнего агента не уходит в ТПУ, токен ТПУ не уходит агенту.
6. **Отзыв действует быстро:** выход, блокировка, отзыв согласия — не дольше 30 секунд для всех каналов.
7. **Утечка одного места не раскрывает всё:** украденная копия БД без ключа шифрования бесполезна; украденный сервисный ключ одного сервиса не открывает другие.

На хосте секреты лежат в `/opt/mytpu/secrets` (0700, владелец — отдельный пользователь), в git — только `.env.example` без значений.

## 4. Токены ТПУ: хранение и продление

**Хранение.** `auth.tpu_tokens(user_id, access_enc, refresh_enc, key_version, expires_at, refresh_expires_at, version, updated_at)`.
Шифр — AES-256-GCM, 12 байт случайного IV на каждую запись, **AAD = `user_id` + имя поля**: шифротекст одного пользователя
нельзя подложить другому, а access — вместо refresh. Готовый `JdbcOAuth2AuthorizedClientService` не годится — хранит открытым текстом.

**Продление — только по требованию, без фоновой задачи.**
1. gateway просит токен у identity (`POST /internal/tpu-token` с паспортом вызова, раздел 5) — identity отдаёт токен только пользователю из паспорта.
2. Если до `expires_at` больше 5 минут — отдаём как есть.
3. Иначе продлеваем под блокировкой **на этого пользователя** (в процессе — `ReentrantLock` из полосатого набора по `user_id`; в БД — оптимистичная проверка `version`). Второй параллельный запрос ждёт и получает уже новый токен. Без этого два продления одним refresh-токеном гасят друг друга.
4. Пришёл новый refresh — сохраняем его и новый `refresh_expires_at` (активный пользователь не перелогинивается никогда).
5. ТПУ ответила `invalid_grant` (неделя без входа или отзыв) → удаляем строку, вызов возвращает `needs_tpu_relink`, клиент показывает «Обновить доступ к ТПУ» (тот же вход).
6. `api.tpu.ru` ответил 401 на свежий токен → одно продление и один повтор, дальше `needs_tpu_relink`.

Фоновое продление «чтобы не протухало» сознательно не делаем: тогда доступ к данным студента жил бы вечно без его участия.

## 5. Как сервисы обмениваются данными

### Паспорт вызова вместо голого `X-User-Id`
Решено 19.10. В документе 22 сервисы доверяют заголовкам `X-User-*` + общему `X-Internal-Key`. Слабое место: кто знает ключ, тот действует
от имени **любого** пользователя. Замена:
- identity на `forward_auth` отвечает не только `X-User-Id`, но и **паспортом** — JWT на 60 с: `sub` = наш userId, `client`, `channel`, `scopes`, `aud` = внутренние сервисы, `jti`; подпись ключом identity.
- caddy срезает входящие `X-User-*` и `X-Passport`, затем кладёт ответ identity.
- assistant, вызывая gateway, пересылает паспорт как есть. gateway проверяет подпись по JWKS identity (кэш), срок и `aud`.
- identity выдаёт токен ТПУ только по паспорту → только тому пользователю, чей запрос идёт сейчас.

Итог: взломанный assistant не может прочитать данные пользователя, который в эту минуту ничего не спрашивает.

### Кто кого вызывает

| Откуда → куда | Адрес | Чем подтверждает |
|---|---|---|
| браузер, мобилка → caddy | `/api/**` | сессия (cookie + CSRF или `X-Auth-Token`) |
| caddy → identity | `/internal/verify` | внутренняя сеть `edge`; ответ: `X-User-*` + паспорт |
| внешний агент → gateway | `/mcp` | мастер-ключ клиента [сейчас]; после identity — ещё и JWT шлюза (`aud` = `/mcp`) |
| консоль → gateway | `/admin/api/**` | ключ администратора + разрешённая сеть [консоль] |
| gateway → rag (консоль) | `/admin/**` | отдельный сервисный ключ gateway → rag-admin [консоль] |
| gateway → стороннее API (коннектор) | HTTPS наружу | секрет коннектора из сейфа gateway, проверка адреса `SsrfGuard` [консоль] |
| assistant → gateway | `/internal/tools/{name}` | сервисный ключ assistant + паспорт |
| gateway → identity | `/internal/tpu-token` | сервисный ключ gateway + паспорт |
| gateway → rag | `/internal/search` | сервисный ключ gateway [сейчас]; данные публичные, паспорт не нужен |
| assistant → ml-server | `/v1/chat/completions` | ключ assistant |
| gateway → ТПУ, Naumen, Moodle | HTTPS наружу | токен ТПУ пользователя / сервисный ключ из сейфа |
| ml-server → LLM | HTTPS наружу | ключ провайдера |

Сервисные ключи — **свой у каждой пары**, а вызываемый держит список «какой ключ к каким адресам допущен»: ключ rag-клиента
не откроет `/internal/tpu-token`. Сравнение — за постоянное время (`MessageDigest.isEqual`).

### Сети Docker Compose [сейчас — для gateway, rag, postgres]
- `edge`: caddy, identity, gateway, assistant — единственная сеть с опубликованными портами (только 80/443 у caddy).
- `core` (`internal: true`, без выхода в интернет): gateway ↔ rag, assistant ↔ ml-server, assistant ↔ gateway.
- `data` (`internal: true`): сервисы ↔ Postgres. Порт 5432 не публикуется.
- Выход в интернет нужен только identity (oauth.tpu.ru), gateway (ТПУ, rasp), ml-server (LLM), rag-ingest (сбор корпуса) — им отдельная сеть `egress`.
- Внутри одной машины трафик не покидает хост, поэтому TLS между контейнерами не ставим; если сервисы разъедутся по машинам — mTLS или WireGuard.

## 6. Данные и LLM

**Политика провайдера** в ml-server — у каждого провайдера два флага:
- `pd_allowed` — можно ли передавать ПД (договор поручения обработки по 152-ФЗ, хранение в РФ). GigaChat, Cloud.ru, YandexGPT по договору — `true`; зарубежные — `false`.
- `pii` — `mask` (метки вместо ПД и обратная замена, в том числе в потоке) или `off`. При `pd_allowed=false` — всегда `mask`.

**Даже при `pd_allowed=true` в модель уходит минимум:**
- инструменты возвращают только нужные для ответа поля (не весь профиль, без id ТПУ, телефона, почты, даты рождения);
- чувствительное (оценки, заявления, медицинское) в модель не уходит вообще: такой инструмент возвращает модели «показано пользователю на карточке», а данные идут в интерфейс напрямую, минуя LLM;
- история диалога в запросе — последние N сообщений, старые ПД вычищаются.

**Уровни доверия модели — одно правило для шлюза и чата.** Модель бывает двух родов: **модель пользователя**
(он сам подключил Claude, ChatGPT или любой агент к `/mcp` — мы не знаем, где она и кто её видит) и **доверенная модель ТПУ**
(её выбирает вуз для нашего чата: своя на серверах ТПУ или российский провайдер по договору). Права у них разные:

| Уровень | Кто это | Публичное | Личное (ПД) | Чувствительное |
|---|---|---|---|---|
| `external` | модель пользователя через MCP: Claude, ChatGPT, свой агент | да | только после входа ТПУ и согласия на scope; зарубежному провайдеру — по решению вуза (вопрос 17) | никогда |
| `trusted_tpu` | модель на серверах ТПУ (vLLM и т. п.) | да | да, минимум полей | только карточкой мимо модели (решение вуза) |
| `trusted_contract` | российский провайдер по договору поручения (GigaChat, YandexGPT) | да | да (`pd_allowed=true`) | карточкой мимо модели |
| `untrusted` | провайдер без договора | да | метки вместо ПД (`pii=mask`) | нет |

Где это решается:
- **MCP (`external`).** Уровень хранится у клиента — в мастер-ключе, позже в политике клиента. Шлюз отдаёт только разрешённое ключом, `SENSITIVE` не выдаёт никогда.
  Доверенный агент самого ТПУ может получить ключ с уровнем `trusted_tpu`, но только решением администратора.
- **Чат (`trusted_*` / `untrusted`).** Шлюз отдаёт данные assistant'у по паспорту пользователя. Что из них уйдёт в модель, решает assistant:
  он сверяется с уровнем провайдера в ml-server. Чувствительное при этом показывается карточкой, минуя модель.
- **Контекст вызова.** В `CallContext` есть `trust`, `senderConstrained` (DPoP) и согласия по scope: сейчас из мастер-ключа
  (всегда `external`, без пользователя) и dev-заголовков, после identity — из JWT.

**Режимы выдачи личного [механизм — сейчас; согласие — identity]** (`specs/personal-data-for-agents`). Инструмент помечает
каждое поле ответа (`@Classified`: `PUBLIC` / `PERSONAL` / `SENSITIVE` + маска `HIDE` / `INITIALS` / `COUNT` / `COARSE`);
личный инструмент без пометки поля не регистрируется — шлюз не стартует. Что отдать, решает шлюз (`DisclosurePolicy`):

| Кто вызывает | Личное | Чувствительное |
|---|---|---|
| свои клиенты (сайт, мобилка) | `full` | `full` (показывается человеку) |
| `trusted_tpu`, `trusted_contract` | `full` | `reference` |
| `untrusted`, чат с недоверенной моделью | `masked` | `reference` |
| `external` без согласия или с истёкшим | отказ `needs_consent` | отказ |
| `external` с согласием | выбранный уровень (по умолчанию `masked`); `full` — только если разрешено вузом (`external-full-allowed`, сейчас нет), без DPoP — не дольше суток, и не после недоверенного текста в сессии (30 мин) | `reference` |

Если хоть одно поле ответа ушло не полностью (в том числе `trusted_*`, где чувствительное — `reference`), фраза `summary`
заменяется безопасной `publicSummary`, `hint` отбрасывается; выбор варианта (`needs_choice`) и текст ошибки личного инструмента
не в режиме `full` заменяются общими текстами; в `reference` нет `data`,
только фраза и ссылка на карточку «Мой ТПУ». Списки личного — не больше `maxItems` (20) на вызов, не больше 200 личных записей
в сутки на пару «пользователь — клиент» (`personal_quota`): записи занимаются до вызова, но не больше остатка, и ответ
обрезается до занятого — лимит не превышается и при параллельных вызовах. Каждая выдача — строка в `gateway.disclosures`
(имена полей, режим, причина; без значений; 1 год).

**Что живёт в памяти шлюза.** Ответ личного инструмента кэшируется **до вырезания** (сырым, как его вернул ТПУ) в памяти
экземпляра — не дольше 60 с, чувствительного — не кэшируется; на диск и в БД кэш не пишется, но дамп памяти процесса
его содержит. Метка недоверенного текста в сессии (`SessionTaint`, 30 мин) — тоже в памяти экземпляра: при нескольких
экземплярах шлюза за балансировщиком её нужно перенести в общее хранилище (Postgres или Redis), иначе другой экземпляр
выдаст `full` после недоверенного текста.

**Внешние агенты (Claude, ChatGPT) — трансграничная передача.** Если студент подключил Claude и дал `profile.read`,
его ПД уйдут американской компании. Это его решение, но экран согласия должен прямо это говорить,
а набор scopes для зарубежных клиентов — ограничиваться политикой клиента (`bus.client_policy`). Решение вуза — вопрос 3.

## 7. Внешние агенты (MCP)
- Свой OAuth-сервер (Spring Security 7), открытая регистрация клиентов (DCR) выключена — клиентов заводит администратор.
- PKCE обязателен всем; `redirect_uri` — точное совпадение.
- `aud` токена = адрес `/mcp` (Resource Indicators, RFC 8707); токены с другим `aud` отвергаются.
- Согласие — по scopes, на русском, с явным «данные уйдут компании X».
- Access 30 мин + ротация refresh; блокировки сверяются каждые 30 с, поэтому блокировка действует быстрее, чем истекает JWT.
- `tools/list` показывает только разрешённые инструменты; `sensitive` наружу нет.
- Анонимного доступа нет: до identity — только мастер-ключи доверенных клиентов (раздел 14) [сейчас].
- Полные требования к OAuth для MCP (метаданные ресурса, ротация refresh с обнаружением повтора, DPoP, `private_key_jwt`)
  и к записи от имени пользователя (черновик, подтверждение по хэшу, окно отмены, правило двух) — `specs/mcp-key-and-agent-safety`, части Б и В.
- В `tools/list` — пометки MCP (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`): это подсказки клиенту, права решает шлюз.

## 8. Подсказки-ловушки (prompt injection)
Текст из внешних источников (статья, заявка, сообщение форума Moodle, страница сайта) может содержать «инструкции» для модели.
- Модель не держит токенов и не ходит в сеть сама — только через инструменты шлюза.
- Нет инструментов, которые отправляют данные по произвольному адресу или произвольному получателю.
- Запись — только черновик + подтверждение человеком на нашем сайте; агент подтвердить не может.
- Результаты инструментов передаются модели в роли `tool` с пометкой «это данные, не инструкции»; ссылки в ответе — только на домены из списка (`*.tpu.ru`).
- Проверки прав — в коде шлюза до вызова, поэтому даже «уговорённая» модель не получит чужих данных.

## 9. Хранение и резервные копии
- У каждого сервиса свой пользователь Postgres с правами только на свою схему; gateway не читает `auth.*`.
- Персональных данных в БД минимум (раздел 1); `auth.users` — без почты, телефона, даты рождения.
- История чата — 30 дней, затем удаление; пользователь может удалить свою историю сам.
- `gateway.audit` — 180 дней; аргументы — SHA-256, IP — для анонимов хранится 30 дней, затем обнуляется.
- Бэкапы — `pg_dump` ночью, шифруются (`age`, публичный ключ на сервере, приватный — у администратора офлайн), хранятся вне машины, проверка восстановления раз в месяц. Без мастер-ключа сейфа токены в бэкапе бесполезны.
- Сессии Spring Session хранят id в открытом виде: утечка живой БД = угон сессий. Смягчение — короткий простой и «выйти везде» при инциденте (вопрос 7).

## 10. Логи
- Никогда в лог: токены, `code`, `client_secret`, заголовки `Authorization`, `Cookie`, `X-Passport`, аргументы и результаты инструментов, тексты сообщений чата.
- Маскирующий фильтр logback на шаблоны токенов (JWT, `Bearer …`, query-параметры `code=`, `token=`).
- В логе: `request_id`, сервис, инструмент, итог, длительность; userId — в виде нашего uuid, не id ТПУ.

## 11. Контейнеры и хост [сейчас — для gateway, rag и assistant]
- Пользователь не root, `read_only: true` (запись только в `tmpfs` для `/tmp`), `cap_drop: [ALL]`, `security_opt: no-new-privileges`.
- Образы с фиксированными версиями и хэшами: база `spring.Dockerfile` закреплена по digest, образ assistant в GHCR
  помечается SHA коммита (без `latest`). CI: gitleaks по всей истории на `main` и `feature/**`, trivy на собранном образе
  (критичная уязвимость с исправлением — стоп). Dependabot на зависимости.
- На хосте: SSH только по ключу, firewall — наружу только 80/443, автоматические обновления безопасности.
- Консоль администратора — роль `admin` + повторный вход ТПУ не старше 10 минут для опасных действий.

| Утекло | Действие |
|---|---|
| Мастер-ключ клиента MCP | `UPDATE gateway.api_clients SET enabled = false …` (≤ 30 с), выдать новый (`issue-key`, для `server` — с `--networks`); по `gateway.key_events` и `audit` понять, откуда и что вызывали |

## 14. Мастер-ключ клиента MCP [сейчас]
Это «один ключ» из документа 20: клиент знает только его, а шлюз по нему решает, какие API открыть, и сам подставляет настоящие ключи сервисов.
- **Что внутри ключа** (в БД, не в самом ключе): владелец; включённые интеграции (scopes); выключенные инструменты; лимиты частоты; «только чтение»; срок; позже — привязка к пользователю ТПУ для личных данных.
- **Формат v2:** `mtpu_` + 43 символа base62 (32 случайных байта) + 6 символов base62 CRC32. Контрольная сумма проверяется
  до запроса к БД (опечатка и мусор → 401 без SQL) и позволяет сканерам секретов ловить ключ без ложных срабатываний:
  правило `mytpu-master-key` в `.gitleaks.toml`, gitleaks — в CI по всей истории. Ключи v1 (`mtpu_` + 43 base64url) действуют до своего срока, новых нет.
- **Хранение:** только SHA-256 (у ключа 256 бит случайности, медленный хэш не нужен); сам ключ показывается один раз при выдаче.
- **Тип ключа:** `server` — интеграция с постоянным адресом, `allowed_networks` обязателен; `person` — человек, без сетей
  ключ живёт не дольше 30 дней. Вызов не из своих сетей → 403 `network_not_allowed`. Адрес клиента берётся из
  `X-Forwarded-For` только от доверенного прокси (`mytpu.gateway.trusted-proxies`, на сервере — caddy).
- **Обнаружение утечки:** шлюз помнит подсети вызовов ключа (IPv4 /24, IPv6 /48 — без полного адреса, 90 дней) в
  `gateway.key_networks`. Новая подсеть → событие `key.new_network`; больше 3 подсетей за час → ключ `server`
  приостанавливается (401 `key_suspended`, снять — `issue-key --resume`), у `person` — событие `key.network_burst`.
  Ключи-ловушки (`issue-key --decoy`) прав не имеют и отвечают как неверный ключ; любое их использование — `key.decoy_used`.
  Все события — в `gateway.key_events` (для консоли) и WARN в лог.
- **Почему это не опасно, хотя ключ «всемогущий»:** он открывает только включённые API, только чтение публичного (до identity), с лимитами;
  прямая запись (`WRITE`) через MCP не выдаётся никогда, только черновики с подтверждением человеком; каждый вызов — в журнале с id ключа;
  отзыв действует за ≤ 30 с; настоящие ключи ТПУ клиент не видит, поэтому утечка мастер-ключа не раскрывает их.
- **Смягчения утечки:** перевыпуск с перекрытием (старый ключ живёт N часов), предупреждение в консоли о ключах без вызовов 30 дней.
- **Дальше** (`specs/mcp-key-and-agent-safety`, части Б и В): внешние агенты — OAuth 2.1 по спецификации MCP вместо ключа
  `person`; свои клиенты — DPoP; серверные интеграции — `private_key_jwt` вместо ключа `server`.

## 15. Консоль и коннекторы [консоль]
- **Доступ:** ключ с ролью `console.admin` или `console.viewer`, плюс список разрешённых сетей; с чужого адреса `/admin/api/**` отвечает 404. Интерфейс держит ключ только в памяти вкладки, выход через 30 минут простоя.
- **Журнал действий:** каждое изменение — `gateway.admin_audit` (было → стало, секреты — `***`).
- **Коннекторы — главный риск SSRF:** администратор вписывает адрес, а запрос делает шлюз изнутри сети. Поэтому `SsrfGuard` при каждом вызове резолвит имя и отвергает частные (10/8, 172.16/12, 192.168/16), loopback, link-local (в том числе 169.254.169.254 — метаданные облака), адреса Docker-сетей и IPv6-аналоги; редирект на другой хост не выполняется; только `https`, ответ ≤ 1 МБ, только JSON, таймаут ≤ 10 с.
- **Коннекторы только читают** (`GET`); их ответ проходит тот же исполнитель (лимиты, кэш, журнал) и помечается для модели как «данные, не инструкции».
- **Загрузка файлов в rag:** только роль администратора; лимиты размера, страниц и времени разбора; файлы — на отдельном томе, не исполняются; текст до индексации проходит `Redactor` (ФИО, телефоны, почта, номера документов).
- **Ненайденные запросы** хранятся уже после `Redactor` и 30 дней.
