# Как сделать систему, в которой справится слабая модель

Задача: «Мой ТПУ» должен нормально работать на GigaChat или YandexGPT — им по договору можно обрабатывать ПД,
но вызовы инструментов, даты и многошаговые цепочки они путают. Значит, ум переносим из модели в систему:
**модель только понимает человека и пересказывает готовое; всё, что можно посчитать, проверить или выбрать кодом, делает код.**

Пометка **[сейчас]** — делается в текущей спецификации (инструменты gateway); остальное — в спецификации assistant и ml-server.

## 1. Путь вопроса

1. **Нормализация (код).** Опечатки и раскладка («ЗФКЫ» → «пары»), номер группы (`8к31`, `8 К 31` → `8К31`), аудитория (`403б`, `к.10 ауд 402`), даты на русском
   («сегодня», «завтра», «в пятницу», «на следующей неделе», «19.10») → точная дата. Парсер дат — свой, детерминированный, с текущей датой и часовым поясом Томска.
2. **Роутер намерений (код, без LLM).** Два уровня: правила (ключевые слова + шаблоны) и классификатор по векторам на примерах фраз
   (модель векторов уже есть в rag). Намерения: «пары на день», «следующая пара», «где аудитория», «дедлайны», «статус заявки», «как сделать / где найти» (документы), «болтовня», «другое».
3. **Слоты из контекста (код).** Группа — из профиля; дата по умолчанию — сегодня; если в прошлом вопросе была группа 8К31, «а завтра?» продолжает её. Слоты диалога хранит сервер, а не память модели.
4. **Прямой путь — без LLM.** Намерение уверенное и слоты заполнены → сервер сам вызывает инструмент и показывает карточку с готовой фразой `summary`.
   Для расписания, ссылок и статусов это большая часть вопросов.
5. **Путь через LLM.** Неуверенно или нужен пересказ → модели дают **3–5 инструментов, выбранных роутером** (не все 20), короткий промпт и уже заполненные слоты.
6. **Проверка ответа (код).** Время, даты, номера аудиторий и заявок в ответе модели должны встречаться в данных инструмента; ссылки — только из данных и только `*.tpu.ru`.
   Не совпало → ответ собирается шаблоном из данных. Модель не может «придумать» пару или ссылку.
7. **Документы — выдержка, а не сочинение.** rag отдаёт фрагмент раздела + ссылку; модель пересказывает в 2–3 предложениях «только из фрагмента».
   Нашлось ли что-то, решает порог rag, а не модель: `found=false` → шаблон «не нашёл, вот как спросить в поддержке».

**Как сделано в assistant (спецификация 5, 06.11.2026).** Ответ модели проверяется до отправки, поэтому в потоке SSE он
приходит одним `delta` после `status` (отправленный кусок не отзовёшь). Весь путь с моделью — не дольше 15 с
(`mytpu.assistant.model-timeout`); модель недоступна, не уложилась или дважды дала неверные аргументы — шаблон из данных
(выдержка с источником) или уточняющий вопрос; модель не вызвала инструмент — его вызывает сам помощник. Код — пакеты
`llm` и `verify` в `services/assistant`.

## 2. Как проектировать инструменты [сейчас]

| Правило | Плохо (для слабой модели) | Хорошо |
|---|---|---|
| Инструмент = задача человека, а не API | `rasp_search` → взять `ref` → `rasp_week` → выбрать день | `rasp_day(group="8К31", date="завтра")` — поиск ref, неделя и день внутри |
| Аргументы человеческие и терпимые | `date` строго `YYYY-MM-DD`, `ref` = хэш | `date`: «завтра», «19.10», «2026-10-19»; `group`: «8к31» — сервер нормализует |
| Мало аргументов, у всех умолчания | 6 полей, 3 обязательных | 1–2 поля; дата по умолчанию — сегодня |
| Перечисления вместо свободного текста | `kind: string` | `kind: "group" \| "room" \| "teacher"` |
| Неоднозначность решает сервер | модель сама выбирает из 12 совпадений | `needs_choice`: 2–5 вариантов + готовый вопрос «Какая группа: 8К31 (ИШИТР) или 8К31 (План)?» |
| Ответ готов к выдаче | сырая таблица на 40 полей | `summary` — готовая фраза; `data` — для карточки; `hint` — что делать дальше |
| Личное — минимум | «Ковалёва Анна, 8К31: 3 дедлайна» внешнему агенту | `publicSummary` — та же мысль без ПД («3 дедлайна, ближайший — через 2 дня»); шлюз отдаёт её всем, кроме `full` |
| Ошибка — это инструкция | `400 Bad Request` | «Не указана группа. Спроси у пользователя номер группы, например 8К31.» |
| Модель не считает | «посчитай чётность недели» | сервер пишет в `summary`: «завтра, 20 октября, чётная неделя» |
| Имена — только латиница, цифры, `_` | `rasp.day` (точку не принимают OpenAI-совместимые API функций) | `rasp_day`, `docs_search` |
| Описание короткое, с примером | абзац про устройство rasp.tpu.ru | «Пары группы на день. Пример: {"group":"8К31","date":"завтра"}» |

Это полезно и внешним агентам через MCP: умному Claude тоже проще с одним `rasp_day`, чем с цепочкой из трёх вызовов.

## 3. Промпт и параметры модели
- Системный промпт на русском, ≤ 1500 токенов: роль, 6–8 правил списком, 3–5 примеров «вопрос → вызов → ответ».
- `temperature` 0,1–0,3; ответ — до 120 слов, если пользователь не просил подробнее.
- В запросе — последние 6 сообщений и слоты; старая история не отправляется (меньше токенов, меньше ПД, меньше путаницы).
- Модели запрещено отвечать фактами без инструмента: «если нет данных инструмента — скажи, что не знаешь, и предложи, где посмотреть».

## 4. Когда модель ошиблась
- Неверные аргументы → сервер возвращает ошибку-инструкцию, модель получает **один** повтор; снова неверно → уточняющий вопрос по шаблону.
- Модель вызвала не тот инструмент (роутер сказал «расписание», а она — «заявки») → запрос не выполняется, вызывается инструмент роутера.
- LLM не ответила за 15 с или вернула мусор → ответ шаблоном из данных инструмента (если они есть) или «попробуйте переформулировать».
- Запись (заявка, справка) — модель только заполняет черновик; человек видит поля на карточке, правит и подтверждает. Ошибка модели здесь ничего не ломает.

## 5. Как выбрать модель — замером, а не на глаз
- Набор из ~100 типичных вопросов (из обращений help.tpu.ru и хакатона) с ожидаемым намерением, инструментом и аргументами; часть — с опечатками, часть — без ответа.
- Метрики: верный инструмент; верные аргументы; ответ сходится с данными (проверка из п. 6 раздела 1); доля ответов без LLM; задержка; цена.
- Прогоняются все кандидаты (GigaChat Lite / Pro / Max, YandexGPT Lite / Pro, локальная Qwen) — берём самую дешёвую, что проходит пороги.
- Тот же набор — регресс-тест при смене промпта или модели.

## 6. Где что живёт

| Часть | Сервис | Почему там |
|---|---|---|
| Нормализация аргументов, `summary`, `needs_choice`, ошибки-инструкции | gateway (инструменты) [сейчас] | одинаково для чата, hub и внешних агентов |
| Нормализация вопроса, роутер, слоты, прямой путь, проверка ответа | assistant | это логика диалога |
| Классификатор по векторам | rag (`POST /internal/classify`) | модель векторов уже там, второй копии в памяти не нужно; отложен — в спецификации 5 сначала правила, классификатор — если правил по оценке не хватит |
| Адаптер GigaChat, политика провайдера (`pd_allowed`, `pii`), таймауты | ml-server | одна точка для всех моделей |
| Набор вопросов и прогон моделей | assistant (профиль `eval`) | рядом с промптом и роутером |

## 7. Что меняется в текущей спецификации [сейчас]
- Инструменты расписания принимают человеческие аргументы: `rasp_day(group, date)`, `rasp_week(group, date)`, `rasp_find(query)` (для аудиторий и преподавателей); `ref` — внутренний.
- Даты — терпимый парсер (`DateArgParser`: «сегодня», «завтра», «послезавтра», дни недели, «19.10», ISO).
- Личные инструменты — ещё `publicSummary` и пометки полей (`docs/ADDING_API.md`); что увидит модель, решает шлюз (`docs/SECURITY.md`, раздел 6).
- Ответ каждого инструмента — `summary` + `data` + `hint`; неоднозначность — `needs_choice`; ошибки — тексты-инструкции из `messages.properties`.
- Имена инструментов — с `_` вместо точки.
