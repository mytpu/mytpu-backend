# Личные данные для внешних агентов: классификация полей, режимы выдачи, согласие со сроком

Опирается на `specs/gateway-public-mcp` (tool-runtime, `ToolExecutor`, `McpResults`), `specs/mcp-key-and-agent-safety`
(часть А — сделана: `untrustedOutput`, пометки MCP; части Б и В — OAuth, DPoP, черновики) и `docs/SECURITY.md`
(раздел 1 — классы данных, раздел 6 — уровни доверия модели `external` / `trusted_tpu` / `trusted_contract` / `untrusted`).

Три части с разной готовностью:
- **А — сейчас, gateway и tool-api.** Механизм: классы полей, решение о режиме, вырезание и маски, безопасная фраза,
  лимиты объёма, журнал выдачи. Проверяется dev-инструментом с вымышленными данными, без настоящего входа ТПУ.
- **Б — вместе со спецификацией 4 `identity`.** Согласие по scope с целью, сроком и режимом; уровень доверия и страна
  клиента в реестре клиентов; всё это — в утверждениях JWT, которые читает шлюз.
- **В — вместе со спецификацией 7 `clients`.** Карточка по ссылке (сами данные — только у пользователя), страница
  «какие мои данные и каким агентам ушли», управление согласиями.

Части Б и В — **обязательные требования** к спецификациям 4 и 7. Личные интеграции (спецификация 6) пишутся уже по этим правилам.

## Зачем
Внешний агент (Claude, ChatGPT, свой агент студента) — модель, про которую мы не знаем, где она работает и кто её видит.
Если студент подключил её и дал доступ к личному, его ФИО, группа, дедлайны и заявки уйдут зарубежной компании.
Цель — чтобы наружу уходил **минимум, нужный для ответа**, по правилам, которые решает шлюз, а не модель;
чтобы пользователь сам выбирал, сколько и на какой срок открыть, и видел, что ушло.

## Принципы
- **Решает шлюз, а не инструмент и не модель.** Инструмент только помечает поля; что отдать — правило шлюза по контексту вызова.
- **Закрыто по умолчанию.** Поле личного инструмента без пометки считается личным; чувствительное наружу не уходит никогда
  (как сейчас, `docs/SECURITY.md` §1).
- **Данные по ссылке лучше маски.** Если агенту для ответа не нужны сами значения, он получает итог («2 долга, ближайший срок —
  через 3 дня») и ссылку на карточку «Мой ТПУ», где данные видит только сам пользователь после входа.
- **Согласие — с целью, сроком и уровнем.** Не «навсегда всё», а «этому агенту — маски, на сутки».
- **Ничего личного не храним дольше вызова** (как сейчас): журнал выдачи — имена полей, не значения; карточка по ссылке хранит
  запрос, а не ответ.

## Режимы выдачи
| Режим | Что получает агент | Когда |
|---|---|---|
| `full` | поля как есть (агентам — без `SENSITIVE`; свои клиенты показывают всё человеку) | свои клиенты (сайт, мобилка) и доверенные модели ТПУ; внешний — только если пользователь сам выбрал `full` для этого клиента и срок не истёк |
| `masked` | личные поля по маске (`HIDE`, `INITIALS`, `COUNT`, `COARSE`), безопасная фраза | внешний агент по умолчанию; любой агент после недоверенного текста в сессии |
| `reference` | только безопасная фраза и ссылка на карточку, без `data` | чувствительное для любого внешнего; режим, выбранный пользователем |
| `deny` | отказ `needs_consent` со ссылкой на экран согласия | нет согласия на scope или оно истекло |

Решение — по полю: публичные поля ответа идут всегда, личные — по режиму, чувствительные — только `reference` для внешних.

## Критерии готовности (проверяемые)

### Часть А — gateway и tool-api, сейчас

**Классификация полей**
- [ ] В `tool-api` есть пометка поля ответа: класс (`PUBLIC` / `PERSONAL` / `SENSITIVE`) и маска (`HIDE`, `INITIALS`, `COUNT`,
  `COARSE`). Поле без пометки получает класс инструмента (`ToolDescriptor.sensitivity`).
- [ ] При старте шлюз проверяет каждый инструмент `PERSONAL`/`SENSITIVE`: у всех полей ответа (включая вложенные записи и
  элементы списков) есть явная пометка; иначе шлюз **не стартует** и называет инструмент и поле. Проверка: убрать пометку у поля
  dev-инструмента → старт падает с понятной ошибкой.
- [ ] У ответа личного инструмента есть безопасная фраза `publicSummary` (без ПД). Нет её — во внешних режимах уходит общая
  фраза из `messages.properties` («Ответ показан в «Мой ТПУ»»), а в журнал — предупреждение об инструменте.

**Решение о режиме и вырезание**
- [ ] Контекст вызова несёт уровень доверия (`external` / `trusted_tpu` / `trusted_contract` / `untrusted`), признак токена,
  привязанного к устройству (DPoP), и согласие (режим, срок) — пока заполняются из ключа и dev-заголовков, после спецификации 4 — из JWT.
- [ ] Правило режима — отдельный класс с таблицей из раздела «Режимы выдачи»; пороги и умолчания — в `application.yml`.
  Проверка: один и тот же вызов dev-инструмента с 6 наборами условий (свой клиент; внешний без согласия; внешний `masked`;
  внешний `full`; внешний `full` с истёкшим сроком; внешний `full` после недоверенного текста) даёт ожидаемый режим по таблице.
- [ ] Вырезание — после кэша и перед журналом и ответом: в `data` нет полей сверх режима, маски применены, `summary` заменена
  на `publicSummary`, если хоть одно поле ушло не полностью; `needs_choice` и текст ошибки личного инструмента
  не в режиме `full` заменяются общими текстами. Проверка: ответ `masked` не содержит ни одного значения из полей `PERSONAL`
  (поиск по тексту ответа MCP, включая `content[0].text`).
- [ ] `SENSITIVE` внешнему агенту — только `reference`, при любом согласии.
- [ ] Недоверенный текст в сессии (инструмент с `untrustedOutput` вызывался тем же клиентом для того же пользователя
  за 30 мин) переводит `full` в `masked` (правило двух).
- [ ] Ответы личных инструментов кэшируются не дольше 60 с, чувствительных — не кэшируются (независимо от настроек инструмента).

**Лимиты объёма**
- [ ] У личного инструмента есть `maxItems` (по умолчанию 20): списки в ответе обрезаются, в ответе — пометка «показано N из M».
  Публичные инструменты не меняются.
- [ ] Личных записей на пару «пользователь — клиент» в сутки — не больше `mytpu.gateway.personal.max-records-per-day`
  (по умолчанию 200); сверх — отказ `personal_quota` до конца суток, событие в журнал. Учёт — в БД (переживает перезапуск).
- [ ] Во внешних режимах список с маской `COUNT` уходит числом (сколько), а «ближайшее» — в `publicSummary`:
  это и есть сводный вид, отдельного флага у инструмента нет.

**Журнал выдачи (основа прозрачности)**
- [ ] Каждая выдача личного — строка в `gateway.disclosures`: пользователь, клиент, инструмент, режим, **имена** выданных
  полей и число записей; значений нет. Хранится 1 год (решение — открытый вопрос 4), чистится по расписанию.

**Проверка без настоящего входа**
- [ ] Dev-инструмент `system_profile_demo` (вымышленные ФИО, группа, дедлайны, «оценки») и dev-способ задать пользователя,
  доверие и согласие заголовками — только при `mytpu.gateway.dev-tools=true` и только с loopback-адреса; при `dev-tools=false`
  заголовки игнорируются. Проверка: тот же запрос с не-loopback адреса → заголовки не действуют.

### Часть Б — согласие и доверие, вместе с `identity`
- [ ] Реестр клиентов OAuth хранит уровень доверия (`external` по умолчанию; `trusted_tpu` — только решением администратора)
  и страну обработки данных (`jurisdiction`); список разрешённых для зарубежных клиентов scopes — политика вуза
  (`mytpu.personal.foreign.*`, решение — вопрос 3 в `docs/SECURITY.md`).
- [ ] Экран согласия по каждому scope: что за данные (на русском, примеры полей), **цель** (из описания клиента), кому и в какую
  страну они уйдут, выбор уровня (`reference` / `masked` / `full`) и срока (1 час / 1 день / 30 дней); для зарубежного клиента
  `full` — только отдельной галочкой о трансграничной передаче (или недоступен, если так решит вуз).
- [ ] Согласие попадает в JWT шлюза: `pd_mode` по scope, `consent_until`; шлюз сверяет их на каждом вызове. Отзыв согласия
  действует за ≤ 30 с (как блокировки).
- [ ] Токен, привязанный к устройству (DPoP, часть Б `mcp-key-and-agent-safety`), отмечается в контексте вызова;
  `full` для `external` без DPoP — не дольше 1 дня, с DPoP — до 30 дней.

### Часть В — карточка и прозрачность, вместе с `clients`
- [ ] Режим `reference` даёт ссылку `…/card/<handle>`: `handle` — случайный, на 24 ч, привязан к пользователю и запросу
  (инструмент + аргументы). Хранится **запрос**, не ответ; страница карточки выполняет запрос заново от имени вошедшего
  пользователя. Чужой пользователь или истёкший `handle` → 404.
- [ ] Страница «Мои данные и агенты»: по каждому клиенту — когда, какие инструменты и **какие поля** ушли, в каком режиме;
  действующие согласия со сроками; «Отозвать» — за ≤ 30 с.
- [ ] Уведомление в приложении при первой выдаче личного новому клиенту.

## Не входит (non-goals)
- Сами личные интеграции (`int-tpuapi`, `int-help`, `int-lms`) — спецификация 6; здесь только правила, по которым они отдают данные.
- Маскирование ПД в тексте, который пишет модель (`pii=mask` в ml-server) — это чат и `assistant`, спецификация 5.
- Анализ содержимого строк на ПД (NER, поиск ФИО в свободном тексте) — классы задаются пометками полей, не угадываются.
- Шифрование ответов «для устройства» и водяные знаки в данных.
- Юридические тексты согласия — их утверждает вуз; здесь — структура экрана и обязательные пункты.

## Ограничения
- Безопасность/данные: значения личных полей не пишутся ни в журнал, ни в логи, ни в `disclosures`; кэш — только в памяти,
  ≤ 60 с; dev-заголовки работают только при `dev-tools=true` и с loopback.
- Архитектура: новый код — в `runtime` (решение о режиме, вырезание, лимиты, журнал выдачи) и `tool-api` (пометки, `publicSummary`,
  уровень доверия в `CallContext`). Новых `*Manager` нет: `DisclosurePolicy` (только решение), `ResultRedactor` (только вырезание),
  `FieldClassifier` (только разбор пометок), `PersonalQuota`, `DisclosureLog`, `SessionTaint`. `ToolExecutor` растёт на один вызов
  редактора и не больше чем до 200 строк — иначе шаг выдачи выносится в отдельный класс.
- Варианты выбора (`needs_choice`) личных инструментов не должны содержать ПД (например, группа вместо ФИО): шлюз их не
  маскирует — это правило контракта инструмента в `docs/ADDING_API.md`.
- Контент: тексты (`needs_consent`, `personal_quota`, общая безопасная фраза, «показано N из M») — `messages.properties`;
  умолчания режимов, сроки, лимиты — `application.yml` (`mytpu.gateway.personal.*`).

## Как устроено (для ревью плана)
- **Путь вызова:** дверь → `CallContext` (+ доверие, DPoP, согласие) → проверки → кэш → вызов инструмента →
  **`DisclosurePolicy.decide(context, tool)` → `ResultRedactor.apply(result, decision)`** → `PersonalQuota` → `DisclosureLog` →
  журнал → `McpResults`.
- **Классы полей** читаются один раз при регистрации инструмента (`FieldClassifier`, отражение по record) и кэшируются.
- **Недоверенный текст:** `SessionTaint` помнит пары «клиент — пользователь» на 30 мин после инструмента с `untrustedOutput`;
  тот же класс использует часть В `mcp-key-and-agent-safety` для пометки черновиков.
