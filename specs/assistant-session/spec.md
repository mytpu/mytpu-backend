# Диалоги помощника после входа

## Зачем

Веб и Android продолжают диалог после входа. В локальном режиме ответы на вопросы о расписании проходят через реальные assistant и gateway, пока вход ТПУ заменён заглушкой.

## Критерии готовности

- [x] После входа помощник создаёт идентификатор диалога. Повторный запрос той же учётки продолжает контекст. Другая учётка получает одинаковый отказ для чужого и неизвестного идентификатора на обоих HTTP-маршрутах.
- [x] Обычный JSON-ответ передаёт идентификатор диалога Android. Веб продолжает получать его в событии SSE `meta`.
- [x] Веб-поток SSE и мобильный JSON прошли через настоящее API помощника и инструмент `rasp_find` шлюза. Публичное расписание вернулось со ссылкой. Для проверки использованы две тестовые учётки.

## Не входит

- Реальный стенд ТПУ, поиск на отдельном экране расписания, личные инструменты, персистентная история, пользовательские лимиты и паспорт вызова.

## Ограничения

- `assistant` проверяет вход через внутренний запрос к `identity`. Идентификатор из браузерных заголовков или тела запроса не принимается. Токены ТПУ не передаются в помощник.
- При пустой настройке `ASSISTANT_IDENTITY_URL` работает прежний клиентский контракт. Связанные с пользователем диалоги хранятся в памяти и не пишутся в старую таблицу истории.
- В JSON появляется дополнительное поле `conversationId`. SSE сохраняет формат.

## Пре-мортем

- Сейчас кэш и точки входа обращаются к диалогу по UUID без владельца. Отказ на чужой или истёкший идентификатор проверяем до вызова модели и записи истории.
- Недоступная identity закрывает доступ. Параллельные записи обновляют только контекст своего владельца. Просроченный диалог нельзя восстановить по старому идентификатору.
