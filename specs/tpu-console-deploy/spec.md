# HTTPS-консоль и выкладка «Мой ТПУ» на сервер ТПУ

## Зачем

Администратор открывает консоль в браузере по адресу `https://mytpu.red.tpu.ru/console/` без SSH-туннеля и локального Angular-сервера. После первоначальной настройки сервер ТПУ сам получает проверенные сборки из GitHub и обновляет стенд. Docker на компьютере владельца для сборки и выкладки не нужен.

## Исходное состояние и задача для DeepSeek

- `deploy/test-server/console.sh` запускает Angular dev-сервер и туннель. `console/proxy.tunnel.json` направляет `/admin/api` на `127.0.0.1:18090`. В `console/angular.json` уже задан `baseHref` равный `/console/`. `deploy/test-server/Caddyfile.mytpu` обслуживает публичные API и отклоняет запросы к админскому API.
- `deploy/compose.dev.yml` и `deploy/compose.test-server.yml` содержат конфигурацию полного стенда. `deploy/compose.server.yml` и `.github/workflows/ci-cd-ai-backend.yml` относятся к отдельной выкладке assistant на VPS. Текущий workflow использует входящие SCP и SSH, недоступные GitHub Actions на сервере ТПУ.
- После согласования реализуй шаги ниже в `mytpu/mytpu-backend`. Перед изменениями прочитай `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md` и правила доступа к консоли в `docs/SECURITY.md`. В конце укажи, какие команды проверки реально выполнил и что осталось проверить на сервере. Для первого запуска оставь готовую инструкцию с командами и параметрами.

## Критерии готовности

### Консоль по HTTPS

- [ ] С разрешённой сети браузер открывает `https://mytpu.red.tpu.ru/console/` с доверенным сертификатом. Прямой переход на вложенную страницу и её обновление работают. UI и относительные запросы к `/admin/api/**` используют один origin. Обычный HTTP перенаправляет на HTTPS.
- [ ] Вариант для согласования — ограничить оба маршрута подтверждёнными сетями ТПУ на входном прокси и сохранить вход по ключам консоли. С разрешённого адреса и действующим ключом `console.admin` администратор входит и выполняет разрешённую операцию. `console.viewer` читает данные, а операция записи отклоняется. Запрос без действующего ключа и запрос из внешней сети с действующим ключом отклоняются. Если доступ нужен извне, согласовать второй фактор на входе, например клиентский сертификат, с учётом общей точки HTTPS для публичных API.
- [ ] Caddy проксирует только `/admin/api` и его дочерние пути на `127.0.0.1:18090`. SPA fallback действует в пределах `/console/`. Основной порт gateway по-прежнему отклоняет админские маршруты, прямой доступ к 18090 извне закрыт. Публичные `/mcp`, `/api/ai/*` и `/actuator/health` сохраняют контракт, включая SSE. Внутренние маршруты и служебные порты недоступны извне.

### CI/CD с загрузкой на сервере ТПУ

- [ ] GitHub Actions собирает production-консоль и образы gateway, rag, assistant под подтверждённую архитектуру сервера, запускает существующие проверки и проверяет готовые контейнеры. Только после успешной проверки всех компонентов публикуется релиз. GHCR хранит образы, релиз содержит манифест с точными digest, SHA исходников и совместимым комплектом файлов выкладки. Включить статику Angular в релиз как образ с digest либо архив с SHA-256. Обновлять и откатывать статику вместе с API. Версия PostgreSQL и том данных сохранены, для разового ingest используется совместимый образ rag.
- [ ] После однократной установки из сети ТПУ сервис и таймер systemd проверяют по исходящему HTTPS выбранный канал релизов GitHub и загружают образы из GHCR. Есть ручной запуск обновления и способ приостановить таймер. В случае закрытого репозитория и пакетов серверу выдаются только права чтения нужных ресурсов. Учётные данные хранятся на сервере отдельными защищёнными файлами. [GitHub Packages](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages)
- [ ] Один запуск обновляет один комплект версий. До переключения загружены все образы и проверены манифест, Compose и конфигурация прокси. Версия считается активной после проверок здоровья и маршрутов. Обрыв загрузки оставляет текущий релиз рабочим. Ошибка запуска или проверки здоровья возвращает предыдущий комплект, включая конфигурацию маршрутов при её изменении. Повтор активной версии пропускается, параллельный запуск блокируется.

### Сборка и передача

- [ ] В репозитории готовы workflow, описание контейнеров, конфигурация запуска и инструкция владельцу сервера. Инструкция описывает исходящий доступ, параметры DNS и TLS, первичную установку, настройку учётных данных, ручное обновление, журнал и откат. Сервер запускает готовые образы через Compose без сборки.
- [ ] Без Docker локально выполнить доступные проверки проекта, включая Maven по `AGENTS.md` и обычную сборку Angular. Проверку контейнеров, Compose и маршрутизации перенести в GitHub Actions. Успешная публикация подтверждается прогоном CI и ссылкой на релиз с digest. При отсутствии авторизованного прогона статус сборки указать отдельно. Реальный DNS, TLS, сетевой доступ и обновление подтверждаются на сервере ТПУ.

## Границы и ограничения

- Затрагиваем выкладку стенда на сервере ТПУ. Миграция ml-server, смена версии PostgreSQL, перенос базы, изменения ролей и переписывание консоли вне объёма задачи. Существующий сценарий отдельного VPS обслуживает свой стенд.
- Определить фактическую точку завершения TLS и место, где достоверно виден адрес клиента. Использовать адрес соединения или явно настроенную цепочку доверенных прокси. Проверить ограничение с разрешённой и внешней сети. Сохранить проверки gateway и запрет произвольных переадресаций в админский API. Ключи и токены исключить из логов, артефактов, образов и репозитория.
- Зафиксировать в `docs/DECISIONS.md` и `docs/SECURITY.md` изменение действующего правила о прямом доступе к порту консоли. На HTTPS-входе срабатывает сетевое ограничение, а на шлюзе используются проверка адреса соединения и существующие роли. Доверие к клиентским заголовкам на порту консоли не расширять. Предусмотреть безопасное начальное состояние с закрытым маршрутом до установки подтверждённого ограничения.
- Скрипт обновления и unit systemd устанавливаются администратором отдельно. Автоматическая выкладка принимает манифест, Compose и артефакты только из настроенного защищённого канала проекта. Разделить файлы релиза и серверные параметры с секретами. При первом запуске определить Compose project name и используемые тома, чтобы подключить ожидаемые данные. Для изменений схемы БД, несовместимых с предыдущим релизом, предусмотреть отдельную процедуру. Откат образов нельзя считать откатом данных.
- Доступ по SSH остаётся административным доступом из сети ТПУ. Выкладка по таймеру использует исходящие соединения сервера.

## Пре-мортем

| Риск | Как проверить |
|---|---|
| Caddy использует публичный порт gateway, либо fallback Angular возвращает HTML на запрос к API | Dev proxy указывает на 18090, а Caddy сейчас закрывает админские пути. В CI проверить вложенный маршрут SPA, API с ключом и отказ на публичном порту |
| Прокси перед Caddy скрывает адрес клиента, и правило допускает всех либо блокирует администраторов | До применения выяснить схему проксирования. Проверить доступ с двух сетей и оба маршрута консоли |
| Релиз опубликован частично или сервер временно потерял доступ к GitHub | Проверить недоступный образ и неполный манифест. Текущая версия должна продолжить работу |
| Таймер и ручной запуск пересеклись, либо новый контейнер поднялся и сразу упал | Проверить блокировку второго запуска, неуспешный health check и восстановление предыдущего комплекта |
| Локальная проверка прошла, но серверный TLS, архитектура образов или права GHCR отличаются | Проверить образ и маршруты в CI. На сервере проверить digest запущенных образов, TLS, доступ из двух сетей и пробное обновление с откатом |

## Открытые вопросы

- Консоль нужна только из сети ТПУ или также из интернета? Для первого варианта нужны разрешённые диапазоны и схема проксирования, для второго — согласованный дополнительный механизм входа.
- Где сейчас завершается HTTPS для `mytpu.red.tpu.ru`, кто управляет сертификатом и какой системный прокси стоит перед приложением? Архитектуру сервера подтвердить командой `uname -m`.
- Какой канал сервер должен подхватывать автоматически? Рекомендуется утверждённый GitHub Release после прохождения CI. Если нужен деплой каждого успешного изменения в `main`, канал должен публиковаться только после тех же проверок.

## Ход работ

Ответы, заложенные в реализацию (25.11.2026):

- Канал — GitHub Release после полного CI, как рекомендовано: `release-tpu.yml` публикует релиз только после `mvn verify`,
  сборки консоли, trivy, смоука готовых контейнеров и маршрутов Caddy. Решение — `docs/DECISIONS.md` за 25.11.
- Архитектура сервера: образы собираются для `linux/amd64` и `linux/arm64`, поэтому `uname -m` не блокирует выкладку;
  подтвердить его всё равно нужно (на случай другого типа).
- HTTPS и сети: оба варианта поддержаны параметром `MYTPU_TLS` (`upstream` — завершение на входном прокси,
  `caddy-cert` — сертификат ТПУ, `letsencrypt`). Сети администраторов — `CONSOLE_ALLOWED_NETWORKS`; пустой список
  закрывает `/console/` и `/admin/api/*` (безопасное начальное состояние). Пока владелец не сообщил диапазоны и точку
  завершения TLS, на сервере действует закрытое состояние — это согласовано с требованием «закрытый маршрут до установки
  подтверждённого ограничения».

Что осталось проверить на сервере ТПУ (критерии готовности не отмечены до этого):

1. DNS и TLS `mytpu.red.tpu.ru`, HTTP → HTTPS, доверенный сертификат в браузере.
2. Доступ с разрешённой сети и отказ с внешней; вход `console.admin`, чтение `console.viewer`, отказ на запись.
3. Digest запущенных образов (`docker inspect --format '{{index .Config.Image}}'`) совпадает с манифестом релиза.
4. Пробное обновление и откат на реальном стенде; `journalctl -u mytpu-update.service`.
5. Запуск rag с моделью векторов (в CI rag не поднимается — нет каталога модели).
6. Первый прогон CI `release-tpu.yml`: ссылка на релиз с digest и статус сборки.
