# Защита ключа MCP от компрометации и пользователя — от действий модели

Опирается на `specs/gateway-public-mcp` (мастер-ключи, `McpKeyFilter`, журнал `gateway.audit`) и `docs/SECURITY.md`
(разделы 3, 7, 8, 12, 14). Источники: спецификация авторизации MCP 2025-11-25, RFC 8707, 9449 (DPoP), 7523
(`private_key_jwt`), 9728; «Agents Rule of Two» (Meta, 2025-10-31). Перед кодом части Б — сверить ревизию MCP 2026-07-28.

Три части с разной готовностью:
- **А — сейчас, только gateway.** Сужает вред от утёкшего мастер-ключа и ловит утечку. Ни от чего не зависит.
- **Б — вместе со спецификацией 4 `identity`.** Внешние агенты переходят с вечного ключа на OAuth 2.1 по спецификации MCP;
  свои клиенты — на токены с привязкой к ключу устройства (DPoP); серверные интеграции — на вход по подписи (`private_key_jwt`).
- **В — вместе со спецификациями 5 `assistant` и 6 `personal-integrations`.** Модель действует от имени пользователя,
  но не может ему навредить: черновики, подтверждение по хэшу, окно отмены, лимиты, журнал для пользователя.

Части Б и В здесь — **обязательные требования**: при написании спецификаций 4–6 их критерии переносятся туда без ослабления.

## Зачем
Мастер-ключ сейчас — «предъявитель»: у кого он есть, тот им и пользуется 90 дней. Вуз указал это как пробел.
Цель — чтобы украденный доступ жил минуты, работал только с устройства владельца (где клиент это умеет),
открывал только безвредное и быстро обнаруживался; а модель, даже «уговорённая» чужим текстом,
не могла сделать необратимого без человека.

## Принципы
- **Нет единственной защиты.** Срок жизни, привязка к владельцу, узкие права, обнаружение и отзыв — слоями.
- **Права решает код шлюза, не модель и не клиент** (`docs/SECURITY.md`, принцип 4).
- **Запись от имени пользователя — только через черновик и подтверждение человеком на нашем сайте.** Через MCP
  инструментов прямой записи нет.
- **Честно о пределах:** Claude и ChatGPT как MCP-клиенты шлют обычный Bearer-токен; DPoP для них недоступен.
  Привязка к устройству — только для наших клиентов и серверных интеграций.
- **Без новых JVM и тяжёлых зависимостей**: всё — в gateway и identity; память машины 4 / 4 не растёт.

## Критерии готовности (проверяемые)

### Часть А — gateway, сейчас

**Формат ключа v2 с контрольной суммой**
- [ ] Новый ключ: `mtpu_` + 43 символа base62 (≥ 256 бит случайности) + 6 символов base62 CRC32 от первых двух частей;
  `issue-key` выдаёт только v2. Ключ v1 (`mtpu_` + 43 base64url) работает до своего `expires_at`, новых v1 нет.
- [ ] Ключ с неверной контрольной суммой отвергается **до** запроса к БД: 401, засчитывается в `AuthFailureLimiter`.
  Проверка: ключ с изменённым последним символом → 401, в журнале SQL — ни одного запроса к `api_clients`.
- [ ] В репозитории `.gitleaks.toml` с правилом для `mtpu_` (v1 и v2); в `ci-build.yml` — шаг gitleaks в контейнере
  (образ закреплён по digest), падает на найденном ключе. Проверка: тестовая ветка с фиктивным ключом v2 → CI красный.

**Ограничение по сетям**
- [ ] У ключа есть `allowed_networks` (список CIDR, IPv4 и IPv6). Пусто — любые адреса; иначе вызов с другого адреса → 403
  `network_not_allowed`, в журнале — исход и сеть (без полного IP).
- [ ] У ключа есть тип: `server` (интеграция с постоянным адресом) или `person`. Для `server` `allowed_networks` обязателен —
  `issue-key` без него отказывает. Ключ `person` без сетей — срок не больше 30 дней (было 90).
- [ ] Адрес клиента берётся из `X-Forwarded-For` **только** если запрос пришёл от доверенного прокси
  (`mytpu.gateway.trusted-proxies`, по умолчанию пусто). Проверка: подделанный `X-Forwarded-For` напрямую на 8081 игнорируется.

**Обнаружение утечки**
- [ ] Для каждого ключа учитываются сети вызовов (префикс /24 для IPv4, /48 для IPv6) с `first_seen` и `last_seen`;
  записи старше 90 дней удаляются. Учёт асинхронный: задержка `/mcp` не растёт больше чем на 1 мс (p95 на замере ПК).
- [ ] Первый вызов из новой сети → событие `key.new_network` (журнал действий + WARN в лог без ключа и полного IP).
- [ ] Больше N разных сетей у одного ключа за час (`mytpu.gateway.key-watch.max-networks-per-hour`, по умолчанию 3) →
  ключ `server` **приостанавливается** (у `person` — только событие `key.network_burst`: мобильный интернет меняет подсети) (`suspended_at`, `suspended_reason`), вызовы → 401 `key_suspended`, событие `key.suspended`.
  Снять приостановку — `issue-key --resume=<id>` (позже — кнопка консоли, спецификация 2). Проверка: 4 вызова ключа `server` с 4 подсетей
  через доверенный прокси за минуту → ключ приостановлен, пятый вызов → 401; ключ `person` — работает, есть событие.
- [ ] Ключ-ловушка: `issue-key --decoy --owner=…` создаёт ключ без прав с пометкой `decoy`. Любой вызов с ним → ответ как на
  неверный ключ (401, тот же текст), событие `key.decoy_used` с сетью и временем. Где раскладывать ловушки — решает администратор.
- [ ] Все события `key.*` видны в одном месте: таблица `gateway.key_events` (кто, что, когда, сеть) — для консоли из спецификации 2.

**Пометки инструментов для клиентов**
- [ ] В `tools/list` у каждого инструмента — `annotations`: `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint` (по описанию инструмента). Это подсказки клиенту; защита от них не зависит.
- [ ] Вид инструмента расширен: `READ` / `DRAFT` (создаёт черновик, ждущий человека) / `WRITE`. Через канал `MCP` инструмент
  `WRITE` недоступен никогда (`tool_not_allowed`), даже если включён ключу. Проверка: тестовый `WRITE`-инструмент в
  профиле dev не виден в `tools/list` и не вызывается.

### Часть Б — OAuth 2.1 для MCP, вместе с `identity`

**Шлюз как сервер ресурса (`gateway`)**
- [ ] `/mcp` принимает JWT шлюза: подпись по JWKS identity, `iss`, `exp`, `aud` = канонический адрес `/mcp` (RFC 8707);
  чужой `aud` → 401. Токены других сервисов дальше не пересылаются (запрет token passthrough).
- [ ] 401 — с `WWW-Authenticate: Bearer resource_metadata="…"`; нехватка прав → 403 `insufficient_scope` с нужным `scope`.
- [ ] `/.well-known/oauth-protected-resource` (и вариант с путём `/mcp`) по RFC 9728: `resource`, `authorization_servers`,
  `scopes_supported` (минимальный набор), `bearer_methods_supported: ["header"]`.

**Сервер авторизации (`identity`)**
- [ ] OAuth 2.1: только `authorization_code` + PKCE `S256` (без PKCE — отказ), точное совпадение `redirect_uri`,
  параметр `resource` обязателен и попадает в `aud`. Access — 15 мин, refresh — 30 дней.
- [ ] **Ротация refresh с обнаружением повтора**: каждый обмен выдаёт новый refresh, старый гаснет; повторное
  предъявление погашенного → вся цепочка (семейство) отзывается, пользователь и клиент видят событие «возможна утечка».
  Проверка: обменять refresh дважды → второй обмен 400 и последующий access из первого обмена тоже перестаёт работать
  (≤ 30 с, как блокировки).
- [ ] Регистрация клиентов: заранее заведённые администратором; документы метаданных клиента (CIMD) — только с доменов
  из списка (решение — открытый вопрос 1); DCR выключен (как в `docs/SECURITY.md` §7).
- [ ] Экран согласия на русском: какие данные, какой компании они уйдут, адрес возврата (хост `redirect_uri` крупно).

**Привязка к устройству для своих клиентов — DPoP (RFC 9449)**
- [ ] Клиенты с пометкой `dpop_required` (сайт, мобилка) получают токены только с DPoP: в токене `cnf.jkt`; без заголовка
  `DPoP` или с неверным доказательством → 401.
- [ ] Проверка доказательства на gateway: подпись ключом из `jwk`, `htm` и `htu` совпадают с запросом, `iat` ± 60 с,
  `ath` = хэш токена, `jti` не повторялся 5 мин (кэш в памяти). Проверка: тот же токен с доказательством от другого ключа → 401;
  повтор того же доказательства → 401.
- [ ] Мобилка: ключ EC P-256 в Android Keystore (StrongBox, где есть), неэкспортируемый. Сайт: ключ WebCrypto
  `extractable: false` в IndexedDB. Описано в спецификации 7 `clients`.

**Серверные интеграции — вход по подписи (`private_key_jwt`, RFC 7523)**
- [ ] Клиент `server` получает токен через `client_credentials`, подтверждая себя JWT, подписанным своим закрытым ключом;
  у нас хранится только открытый ключ (JWKS клиента). Утверждение живёт ≤ 5 мин, `jti` одноразовый; токен — 10 мин.
- [ ] После этого мастер-ключи `server` переводятся на подпись с датой отключения (по умолчанию 60 дней), мастер-ключи
  `person` — на OAuth; `issue-key` новых ключей `person` не выдаёт.

### Часть В — пользователь против действий модели, вместе с `assistant` и `personal-integrations`

**Черновик и подтверждение по хэшу**
- [ ] Инструмент `DRAFT` сохраняет черновик: пользователь, инструмент, данные в каноническом JSON, `payload_hash` (SHA-256),
  клиент, пометка `tainted`, статус `draft`; срок 24 ч.
- [ ] Подтверждение — только на нашем сайте (или в мобилке) человеком под своим входом; у MCP и чата нет способа подтвердить.
  Экран показывает **ровно то, что уйдёт** (поля, получатель) и что было изменено человеком.
- [ ] Подтверждение одноразовое и привязано к `payload_hash`: если данные черновика изменились после открытия экрана —
  подтверждение отвергается, экран перерисовывается. Проверка: изменить черновик между показом и «Подтвердить» → отказ.
- [ ] **Повторный вход (step-up)** для записи с данными `PERSONAL`/`SENSITIVE` и для необратимых действий: вход ТПУ
  не старше 5 мин (`auth_time`), иначе — повторный вход (зависит от вопроса 3).

**Окно отмены и лимиты**
- [ ] Подтверждённое действие уходит не сразу: статус `scheduled`, отправка через N мин (`mytpu.drafts.undo-window`,
  по умолчанию 5); кнопка «Отменить» до отправки. Проверка: подтвердить и отменить через минуту → во внешний сервис
  ничего не ушло, статус `cancelled`.
- [ ] Лимиты: не больше N черновиков и M отправок на пользователя в сутки (конфиг), не больше K на клиента; сверх — понятная ошибка.

**Правило двух (prompt injection)**
- [ ] У инструментов есть признак «возвращает недоверенный текст» (форумы Moodle, тексты заявок, внешние страницы).
  Если такой инструмент вызывался тем же клиентом от имени того же пользователя за последние 30 мин, новые черновики
  получают `tainted=true`: на экране подтверждения — предупреждение и обязательная галочка «я проверил текст»
  плюс повторный вход.
- [ ] Инструментов, которые отправляют данные по произвольному адресу или произвольному получателю, нет (как сейчас);
  ссылки в ответах — только на домены из списка.

**Прозрачность для пользователя**
- [ ] Страница «Что делали агенты от моего имени»: по каждому подключённому клиенту — вызовы (инструмент, время, итог,
  без аргументов), черновики и их судьба; кнопка «Отключить клиента» отзывает его refresh-токены за ≤ 30 с.

## Не входит (non-goals)
- Обход ограничений сторонних клиентов: DPoP для Claude/ChatGPT, пока они его не поддерживают.
- Медленный хэш или «перец» для мастер-ключа: у ключа 256 бит случайности, утечка хэшей ничего не даёт.
- Геолокация и база ASN (MaxMind и т. п.) — обнаружение по подсетям без внешних баз.
- Уведомления по почте или в мессенджер о событиях `key.*` — пока журнал и лог; канал уведомлений — отдельно.
- Интерфейс консоли для событий ключей — в спецификации 2 (здесь — таблица и данные для неё).
- Где раскладывать ключи-ловушки — организационное решение администратора.
- Реализация самого OAuth-сервера, сейфа токенов и экранов клиентов — в спецификациях 4 и 7; здесь только требования к ним.

## Ограничения
- Безопасность/данные: ключи в журнал и логи не попадают (только префикс); IP хранится только префиксом подсети, 90 дней
  (152-ФЗ); секреты — файлами (`deploy/secrets`), их не читать. Не трогать незакоммиченную правку `docs/SECURITY.md`
  (раздел «Уровни доверия модели») без согласования с её автором.
- Архитектура: часть А — пакет `access` gateway и `tool-api` (вид инструмента); новых `*Manager` нет: учёт сетей —
  отдельный класс `KeyNetworkWatch`, политика сетей — `NetworkPolicy`, формат — `ApiKeys`. `McpKeyFilter` не растёт сверх 200 строк.
  Части Б и В — в `identity`, `gateway.mcp`, `assistant` и модуле черновиков (решить в спецификации 6).
- Контент: пороги, окна, лимиты — в `application.yml` (`mytpu.gateway.key-watch.*`, `mytpu.drafts.*`); тексты ошибок —
  `messages.properties`; описания и пометки инструментов — `tools/descriptions.properties`.

## Как устроено (для ревью плана)
- **Путь вызова с ключом (А):** `McpKeyFilter` → формат и CRC (без БД) → `AuthFailureLimiter` → поиск по хэшу →
  `decoy`? → `suspended`? → `NetworkPolicy` (адрес клиента через доверенный прокси) → вызов; после ответа —
  асинхронно `KeyNetworkWatch.record(client, subnet)` → при новой сети или превышении — `key_events` и приостановка.
- **Путь с OAuth (Б):** агент → 401 + `resource_metadata` → метаданные → вход ТПУ и согласие в identity →
  JWT (`aud`=`/mcp`, при DPoP — `cnf.jkt`) → gateway проверяет подпись, `aud`, scope, DPoP → тот же `CallContext`.
- **Путь записи (В):** модель → инструмент `DRAFT` → черновик (`payload_hash`, `tainted`) → пользователь на сайте
  (step-up при необходимости) → подтверждение по хэшу → `scheduled` → окно отмены → отправка интеграцией → журнал.
