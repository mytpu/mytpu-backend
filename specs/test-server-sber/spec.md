# Тестовая выкладка на сервер Сбера (до ВМ ТПУ)

Сервер ТПУ ещё не выдан; тестовый сервер Сбера доступен (Ubuntu 24.04, там уже работают ml-server как служба systemd
и Caddy с Let's Encrypt на домене `sslip.io`). Проверяем весь стенд в боевых условиях: HTTPS, доверенный прокси,
настоящие адреса клиентов, память под нагрузкой. Полноценный прод — спецификация 3 `deploy-server` на ВМ ТПУ.

## Зачем
Убедиться до ВМ ТПУ, что стенд поднимается не на ПК разработчика: MCP-шлюз отвечает по HTTPS, Claude Code
подключается по ключу, защита ключей работает с настоящими адресами (сети, «только из России», ловушки), консоль
доступна только через SSH-туннель. И получить замер памяти вместо оценки 2,6–2,9 ГБ — для заявки на сервер ТПУ.

## Критерии готовности (проверяемые)
- [ ] Образы gateway, rag, assistant собираются на ПК одной командой и переносятся на сервер одним архивом
  (`docker save` → `scp` → `docker load`); на сервере ничего не компилируется.
- [ ] На сервере одна команда поднимает postgres, rag, gateway, assistant с лимитами памяти стенда; секреты создаются
  на сервере (в git их нет); ml-server не трогаем — assistant ходит в него по `127.0.0.1`.
- [ ] Caddy: отдельный сайт `mytpu.<ip>.sslip.io` (сертификат Let's Encrypt). Наружу — только `/mcp`, `/actuator/health`,
  `/api/ai/*`; `/admin/*` и `/internal/*` — 404 на уровне Caddy. Шлюз доверяет адресу Caddy (`TRUSTED_PROXIES`).
- [ ] `https://mytpu.<ip>.sslip.io/actuator/health` → `UP`; Claude Code по `claude mcp add … /mcp` с ключом из
  `issue-key` отвечает через `docs_search`; неверный ключ → 401.
- [ ] Защита на настоящих адресах: ключ `server` с чужой сетью → 403; ключ «только РФ» с иностранного адреса (VPN) →
  приостановлен; ловушка → группа приостановлена; события видны в консоли.
- [ ] Консоль: на ПК `npm run start:tunnel` + `ssh -L 18081:127.0.0.1:8081 …` → вход ключом консоли; без туннеля и
  через Caddy консоль недоступна.
- [ ] Замер: `docker stats` в покое, при загрузке корпуса в rag и под 20 параллельными вызовами `docs_search` — цифры
  в `deploy/test-server/README.md` и в базе знаний.
- [ ] Остановка одной командой; сервер возвращается к прежнему состоянию (ml-server работает, свой Caddy-сайт удалён).

## Не входит (non-goals)
- Постоянная работа и мониторинг, резервные копии, CI-выкладка — это сервер ТПУ (спецификация 3).
- Вход через ТПУ (identity) и личные данные — их нет до ключей ТПУ.
- Нативная сборка ml-server, перенос ml-server в Docker.
- Раздача консоли через Caddy (на тесте — только туннель).

## Ограничения
- Безопасность: адрес сервера, ник и ключи — не в git (`deploy/test-server/server.env` в `.gitignore`, пример —
  `server.env.example`); секреты — файлами, создаются на сервере `dev-secrets.sh`; порты сервисов — только `127.0.0.1`.
- Память: сколько свободно на сервере рядом с ml-server — узнаём первым шагом; если меньше 3 ГБ — поднимаем без
  assistant и rag-ingest.
- Архитектура: новый оверлей поверх `compose.dev.yml` (образы по тегу без сборки, адреса и прокси для сервера), без
  второй копии описания сервисов.

## Ответы на открытые вопросы (2026-10-31)
1. Доступ — SSH по ключу с ПК владельца, пользователь без прав администратора (как при выкладке ml-server). Команды
   с правами администратора (установка Docker, добавление в группу `docker`, правка `/etc/caddy/Caddyfile` и перезагрузка
   Caddy) выполняет владелец по памятке; остальное (перенос, запуск, проверки) — Claude по SSH, с разрешения на каждый шаг.
2. Сервер: 4 ГБ (свободно ≈ 3,2 ГБ при работающем ml-server), 2 ядра, диск 45 ГБ (свободно 38). Docker не установлен.
   Стеку без identity нужно ≈ 2,0–2,4 ГБ — помещается; загрузка корпуса в rag — отдельным запуском, не вместе с
   нагрузочной проверкой.
3. Корпус и модель rag переносим.
