# Защита шлюза от перегрузки и чужих страниц (по проверке стенда 01.11)

Проверка безопасности стенда Сбера (`specs/test-server-sber/security-check.md`) нашла места, где шлюз выдерживает
обычного злоумышленника, но не того, у кого много адресов или кто действует через браузер жертвы. Эта спецификация
закрывает пункты 1, 3, 4 и 5 оттуда; ограничение соединений в nftables, обновления Ubuntu и SSH — владелец сервера.

## Зачем
- Сейчас лимит неудачных ключей считается по одному адресу (IPv4) или /64 (IPv6). У кого есть IPv6 /48 — это
  65 536 «адресов»: перебором он выбирает общий бюджет поиска ключей в БД (50 в секунду), и настоящие ключи после
  истечения кэша (30 с) получают `401 invalid_token`. Клиенты MCP считают такой ключ отозванным — это отказ в
  обслуживании, похожий на отзыв.
- Один ключ может открыть сколько угодно одновременных запросов `/mcp` (в том числе долгих потоков) и занять все потоки.
- Спецификация MCP требует проверять `Origin`: без проверки страница в браузере жертвы может достучаться до шлюза
  через DNS rebinding (особенно опасно, когда шлюз доступен по локальному адресу).
- ml-server открыт в интернет (с ключом), хотя ходить в него должен только помощник с того же сервера.

## Критерии готовности (проверяемые)
- [x] Неудачные ключи считаются ещё и по широкой подсети (/24 IPv4, /48 IPv6) с отдельным порогом
  (`mytpu.gateway.access.max-failures-per-subnet-per-minute`, по умолчанию 300): сверх — `429 too_many_attempts` с
  `Retry-After`, без обращения к БД. Порог по одному адресу (30) остаётся.
- [x] Бюджет поиска ключей в БД исчерпан → `503 key_lookup_busy` с `Retry-After: 1`, а не `401`; такой ответ не
  считается неудачей адреса. Неизвестный ключ при свободном бюджете — по-прежнему `401 invalid_token`.
- [x] Не больше N одновременных запросов на ключ (`mytpu.gateway.access.max-concurrent-per-key`, по умолчанию 8);
  сверх — `429 too_many_concurrent` с `Retry-After: 1`. Разрешение освобождается и для асинхронных (потоковых)
  ответов — по завершении, ошибке или таймауту; для `/actuator/health` и консоли лимита нет.
- [x] `/mcp`: запрос с заголовком `Origin`, которого нет в `mytpu.gateway.mcp.allowed-origins` (по умолчанию пусто),
  → `403 origin_not_allowed`; без `Origin` (Claude Code, серверные клиенты) — как раньше.
- [x] Юнит-тесты шлюза (JUnit 5, `mvn verify`): `StrictPathFilter` (опасные и обычные пути), широкий лимит, 503 при
  исчерпанном бюджете, лимит одновременных запросов (в том числе асинхронный ответ), проверка `Origin`.
- [x] Стенд Сбера: новые ответы проверены снаружи (`Origin: https://evil.example` → 403; 9 одновременных долгих запросов
  одним ключом → хотя бы один 429; обычный вызов Claude-совместимым клиентом — 200).
- [ ] ml-server снаружи закрыт: сайт ml-server в Caddy отвечает только запросам с сети `edge` стенда и с самого сервера
  (готовый основной Caddyfile — `deploy/test-server/Caddyfile.main`, применяет владелец); чат через помощника работает,
  запрос к `https://<домен ml-server>/v1/…` с ПК → 403.
- [x] `docs/SECURITY.md` и `security-check.md` отражают сделанное; `docs/DECISIONS.md` — строки решений.

## Не входит (non-goals)
- Ограничение соединений на уровне ядра (nftables), обновления Ubuntu, настройка SSH и fail2ban — владелец сервера
  (команды — в `security-check.md`).
- Отдельный порт консоли или mTLS для туннеля (пункт 6) — со спецификацией сервера ТПУ.
- `trivy` в CI и закрепление `pgvector` по digest — со спецификацией сервера ТПУ (CI-выкладка).
- Лимиты помощника (`/api/ai/*`) — в спецификации 5 `assistant`.

## Ограничения
- Безопасность: новые отказы не раскрывают, существует ли ключ (тексты — общие, как у `invalid_token`); 503 не выдаёт
  настоящий ключ за отозванный.
- Память: счётчики — Caffeine с ограниченным размером и сроком, как у `AuthFailureLimiter`.
- Архитектура: `McpKeyFilter` не растёт — лимит одновременных запросов и `Origin` — отдельные фильтры после него;
  результат поиска ключа — тип с тремя исходами вместо `Optional`.
