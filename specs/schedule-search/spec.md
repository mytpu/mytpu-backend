# Поиск публичного расписания в вебе и Android

## Зачем

После входа пользователь может найти расписание группы, преподавателя или аудитории по одному запросу и открыть календарь на сайте ТПУ. Для демо подходят существующие тестовые сессии и живой источник публичного расписания через шлюз.

## Критерии готовности

- [x] С активной веб-сессией или мобильным токеном поиск возвращает результаты `rasp_find` одинаковой структуры и в порядке шлюза. Пользователь видит название, тип и пояснение при наличии. Ссылка открывает календарь на сайте ТПУ.
- [x] Тот же запрос без сессии, с просроченной или отозванной сессией получает `401` без вызова шлюза. Если identity недоступен или его адрес не задан, API возвращает `503` без вызова шлюза.
- [x] Ввод обрезается по краям. Пустой, состоящий из пробелов или длиннее 100 символов после обрезки запрос возвращает `400` без вызова шлюза.
- [x] При отсутствии совпадений приходит `200` с пустым списком. Таймаут и сбой источника отображаются как ошибка с возможностью повторить запрос.
- [x] Веб использует существующий экран «Расписание». Блок с демонстрационными парами помечен как демонстрационный отдельно от живого поиска. Android добавляет «Расписание» в авторизованную часть приложения.
- [x] Оба клиента показывают ожидание, результаты, пустую выдачу и ошибку, а при `401` возвращают к входу через имеющийся поток. Ответ старого запроса не перезаписывает более свежую выдачу и не появляется после выхода.
- [x] Сквозная проверка на тестовой учётке подтверждает поиск группы, преподавателя и аудитории, пустую выдачу и отказ без сессии. Чат по-прежнему умеет искать расписание.

## Не входит

- «Мои пары», выбор своей группы, расписание по дням и неделям внутри приложения, детали занятий (`rasp_day/week`).
- Подключение реального OAuth ТПУ, выкладка на внешний стенд и отдельная проверка возврата из браузера на Android.

## Ограничения

- Новый маршрут `POST /api/ai/schedule/search`, тело JSON `{"query":"8К31"}`. Успех — `{"total":1,"items":[{"name":"8К31","kind":"группа","hint":null,"url":"https://rasp.tpu.ru/redirect/kalendar.html?hash=…"}]}`. `total` — число совпадений по данным шлюза, `items` — до 10 результатов. `kind` — подпись из шлюза, `hint` — строка или `null`. Ответ с результатами передаётся с `Cache-Control: no-store`.
- Ошибки JSON со стабильным полем `error`: `400 invalid_query`, `401 session_required`, `503 identity_unavailable`, `503 schedule_unavailable`, `504 schedule_timeout`. Клиенты показывают собственные понятные сообщения.
- Маршрут принимает существующую cookie или мобильный Bearer и всегда проверяет сессию через `/api/auth/session`. Параметры режима чата и заголовки клиента не могут отключить эту проверку. Серверный ключ остаётся в `assistant`/доверенном прокси по существующей схеме, а шлюз получает только запрос поиска и свой служебный ключ. Сессии и тела запроса не пишутся в новые журналы.
- `assistant` использует `GatewayToolsClient` и структурированный ответ `rasp_find`. Поиск работает без модели, без создания диалога и без новых таблиц. Контракты чата, identity и шлюза сохраняются. Прокси локального веба направляет новый маршрут в тот же `assistant`, сохраняя защиту и доставку сессии.
- Действует общее ограничение `assistant` на размер тела. Поиск использует отдельные от чата счётчики частоты и одновременных запросов с теми же настройками. Лимиты применяются до обращения в identity. При превышении лимита `assistant` возвращает `429` с `Retry-After`.
- Клиенты открывают только HTTPS-ссылки на `rasp.tpu.ru`. Веб использует текущие компоненты и токены, Android — текущую тему Compose и строки из ресурсов.

## Пре-мортем

- Проверено по коду: `RaspFindTool` возвращает `total` и `items` с типом, пояснением и ссылкой. `GatewayToolsClient` передаёт структурированные данные в `ToolAnswer`. `ChatSession.owner` допускает пустой идентификатор в старом режиме чата. Для поиска понадобится обязательная проверка сессии с отдельным тестом на пустой `ASSISTANT_IDENTITY_URL`.
- При сетевом сбое источник может не ответить, а при изменении формата вернуть некорректные данные. Таймаут или некорректный ответ шлюза должны привести к ошибке API. Отличие ошибки от корректной пустой выдачи закрепляется тестами. Вывод пустой выдачи при изменении формата страницы ТПУ проверяется живым поиском по известной группе.
- Запросы поиска выполняются независимо и читают данные. При повторной отправке клиент отменяет или игнорирует предыдущий запрос. При выходе клиент сбрасывает выдачу и игнорирует запоздавшие ответы. Проверяем последовательность «A, B, приходит B, приходит A».
- Источник ожиданий для автопроверок — контракт выше и структура `RaspFindTool.Answer`. Проверки на заглушках используют фиксированные ответы, а живой прогон проверяет признаки результата и ссылку, поскольку состав выдачи может измениться.
- `verify.sh` не проверяет проксирование Vite, клики по ссылкам и экран Android. Веб проверяем в отдельном локальном браузерном тесте. Android собираем и проверяем логику и сетевой контракт тестами. Если устройство доступно, дополнительно проверяем экран и открытие ссылки, иначе явно фиксируем статус в отчёте.

- 2026-11-22 — бэкенд прошёл `bash .claude/verify.sh`. С временно отключённой обязательной сессией тест маршрута получил `200` вместо `503`. После восстановления проверки тест прошёл.
- 2026-11-22 — веб прошёл сборку, lint и тесты. Браузерная проверка покрыла тестовый вход, переход по ссылке, пустую выдачу, повтор после ошибки, возврат ко входу при `401` и запоздавший ответ.
- 2026-11-22 — Android прошёл сборку APK и пять тестов поиска. Тесты подтвердили метод, путь, Bearer и JSON через локальный HTTP-сервер, сброс выдачи и защиту от запоздавших ответов. ADB не показал подключённого устройства, экран и открытие ссылки на Android проверяются при подключении.
- 2026-11-22 — сквозной прогон подтвердил выдачу группы `8К31`, преподавателя по запросу «Стрижак», аудитории по запросу `403` и пустую выдачу. После остановки identity поиск возвращает `503`. Исчерпание лимита поиска оставляет доступными запросы чата. По итогам архитектурного ревью и ревью безопасности добавлены явные таймауты, отдельный лимит поиска, проверка HTTPS и линейная обработка пробельного ввода. Повторный прогон прошёл.
