# Вход в «Мой ТПУ» через единую авторизацию ТПУ

## Зачем

Веб и Android открывают официальный вход ТПУ. Пользователь вводит корпоративный логин и пароль на странице ТПУ и возвращается в приложение со своей сессией «Мой ТПУ».

## Критерии готовности

- [x] В вебе и собираемом Android-проекте `MyTpu/` добавлена кнопка «Войти через ТПУ». Заглушки соцвхода удалены из собираемого проекта. Отдельное дерево макетов `app/` не участвует в сборке.
- [ ] Android открывает системный браузер и принимает возврат по подтверждённой HTTPS-ссылке приложения. На локальном мок-стенде используется отладочный URI. Возврат на устройстве ещё предстоит проверить.
- [x] Веб с заглушкой получает сессию и показывает профиль. Отклонение отмены, неверного или повторного `state` и повторного callback проверено. Для Android серверный обмен проверен по HTTP, проверка UI на устройстве остаётся открытой.
- [ ] Выход отзывает локальную сессию. Обновление токена ТПУ происходит на сервере, а при невозможности обновить его клиент предлагает повторить вход.

## Не входит

- Собственная регистрация, пароли и подтверждение по почте.
- OAuth-сервер для внешних MCP-агентов и персональные инструменты ТПУ. Удаление Telegram из служебных оповещений описано отдельно.

## Ограничения

- `services/identity` управляет сессиями и выполняет обмен с ТПУ. Сайт и callback используют один HTTPS origin. Бэкенд проверяет одноразовый `state`, обменивает код по `/access_token` и получает профиль по `/user`. На вебе локальная сессия передаётся через `HttpOnly` cookie. Android обменивает одноразовый результат перехода, привязанный к запросу приложения, на локальную сессию. Отладочная сборка и профиль `mock` поддерживают локальный возврат.
- Токены ТПУ и `client_secret` хранятся на сервере. Код, токены, секрет и полные URL запросов обмена исключаются из журналов и телеметрии. Корпоративный пароль обрабатывает ТПУ.
- [Процесс авторизации](https://devdocs.tpu.ru/books/edinaia-avtorizaciia-tpu/page/process-avtorizacii) и [обновление токена](https://devdocs.tpu.ru/books/edinaia-avtorizaciia-tpu/page/vosstanovlenie-avtorizacii) задают внешний контракт. ТПУ документирует серверный обмен через GET. Таблица обмена требует `state`, хотя в примере его нет. В спецификации берём за основу таблицу и проверяем обмен на стенде.

## Пре-мортем

- На реальном стенде обмен зависит от одобрения приложения и настроек доверенных адресов в API ТПУ. Локальные тесты проверяют контракт с заглушкой, а вход с корпоративной учёткой проверяется отдельно.
- При ошибке обмена сессия не создаётся. Два callback для одного запроса дают максимум одну сессию. Параллельные обновления одной сессии согласуются на сервере.

## План

| Шаг | Файлы | Проверка |
|---|---|---|
| ✅ Добавить вход, callback, сессии и выход | `services/identity/`, `services/pom.xml`, `deploy/` | Успешный обмен, отмена, неверный и повторный `state`, отказ заглушки ТПУ и выход. Сборка через `bash .claude/verify.sh` |
| ✅ Подключить веб | `mytpu/frontend`, оболочка приложения и HTTP-клиент | Вход, профиль, обновление страницы и отзыв сессии в headless Chromium |
| Подключить Android | `mytpu/mobile`, `AndroidManifest.xml`, `LoginScreen.kt`, `AuthViewModel.kt` и HTTP-клиент | APK, unit-тесты и тестовый APK собраны. Обмен, отказ при повторе, чат и выход проверены по HTTP. Проверка Android UI и возврата с браузера открыта |
| Прогнать сквозной сценарий на стенде | `deploy/test-server/` | Отложено до получения параметров авторизации ТПУ |
