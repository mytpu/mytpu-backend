# Исправление HTTPS-консоли и выкладки на сервер ТПУ

## Зачем

Довести реализацию из `c2c205a` до первого рабочего релиза. Администратор открывает `https://mytpu.red.tpu.ru/console/` без SSH-туннеля, а сервер ТПУ сам скачивает и применяет проверенный комплект по исходящему HTTPS. [Исходная спецификация](../tpu-console-deploy/spec.md)

## Задача для DeepSeek

После согласования исправь реализацию по плану ниже. Начни с регрессий на чистую установку, неудачное обновление и установку рядом с уже работающим Caddy. При проверке отката сравнивай фактические файлы и конфигурацию, с которой запущены сервисы. Локальный прогон на заглушках уже давал 33 успешные проверки при отсутствующем Compose-файле на первом запуске.

## Критерии готовности

### 1. HTTPS и установка Caddy

- [ ] `install.sh` подключает площадку «Мой ТПУ», сохраняя существующие сайты, импорты и глобальные настройки Caddy. Повторная установка не дублирует импорт. Невалидный итоговый конфиг или ошибка reload оставляет прежние файлы и рабочую конфигурацию. Проверить на конфиге с отдельным сайтом и с ошибкой в новом импорте.
- [ ] В режиме `upstream` Caddy явно слушает только loopback. Указать, какой `Host` передаёт входной прокси, где выполняются HTTP → HTTPS и сетевое ограничение для `/console/` и `/admin/api/**`. Согласованная цепочка прокси сохраняет реальный адрес клиента для публичных сервисов, которым он нужен для лимитов и геополитики ключей. При отсутствии подтверждённого ограничения оба маршрута консоли закрыты. Режим с прямым TLS применяет ограничения в Caddy.
- [ ] Из разрешённой сети консоль и вложенные страницы открываются по HTTPS. `console.admin` выполняет разрешённую операцию, `console.viewer` читает данные и получает отказ на запись. Внешний запрос к консоли с действующим ключом отклоняется. Публичные маршруты и SSE работают по прежнему контракту, служебные порты и внутренние маршруты закрыты извне.
- [ ] Загрузка поддерживаемого документа размером более 2 МБ и до 20 МБ проходит через API консоли. Публичные API сохраняют свой лимит 2 МБ. Проверки используют Caddy и настоящий gateway.

### 2. Установка и обновление стенда

- [ ] На чистой установке без `state/compose.yml` обновлятор проверяет и запускает Compose из целевого релиза. PostgreSQL на новом томе получает скрипт инициализации до первого старта. При следующем обновлении применяется новый Compose вместе с образами и статикой, существующие тома сохраняются.
- [ ] До запуска целевого релиза скачаны все образы, проверены манифест, Compose и итоговая конфигурация Caddy с импортами. Обрыв загрузки, неверный Compose и неверный Caddy не меняют активные файлы, записанную версию и запущенные контейнеры. Параллельный запуск пропускается.
- [ ] Успех фиксируется после проверки здоровья PostgreSQL, rag, gateway, assistant и маршрутов. При ошибке после начала переключения восстанавливается фактический предыдущий комплект. Проверить отдельно сбой до изменения Caddy и после него. Ручной откат проверяет здоровье и маршруты перед записью активной версии. После неудачного первого запуска активная версия отсутствует, состояние позволяет повторить установку.
- [ ] Контейнерные секреты читаются реальными пользователями PostgreSQL и Spring, включая UID `10001`. Родительский каталог закрыт для обычных пользователей хоста, токен GitHub остаётся отдельным файлом `0600` и не монтируется в контейнеры. В CI проверяются права, которые выставляет установщик.

### 3. CI, публикация и передача

- [ ] Workflow скачивает архив Caddy под именем, которое сверяется через файл контрольных сумм. Ошибка проверки останавливает запуск. Перед публикацией образов workflow авторизуется в GHCR. Публикация идёт только из защищённой `main`, включая ручной запуск. Ручной запуск с другой ветки может прогнать проверки, но не публикует образы, теги и релизы.
- [ ] CI прогоняет Compose и проверки маршрутов на готовых контейнерах, включая проверку запуска rag с документированным тестовым ресурсом. Проверенный комплект привязан к опубликованным digest. Для архитектуры сервера проверены сборка, запуск и применимость образов. Релиз, который скачивает таймер, становится доступен только после всех обязательных проверок и загрузки всех файлов.
- [ ] Обновлятор скачивает файлы приватного GitHub Release через API release assets с `Accept: application/octet-stream` и учётными данными только на чтение. В инструкции описаны права и параметры для чтения релиза и GHCR, начальная настройка до включения таймера, выпуск первого ключа консоли, ручной запуск и откат.
- [ ] Перед передачей приложить результаты локальных проверок и указать статус каждого внешнего прогона. Готовность релиза подтверждается ссылкой на успешный GitHub Actions и опубликованный комплект с digest. Готовность выкладки подтверждается проверкой на сервере ТПУ из разрешённой и внешней сети, первым запуском и пробным обновлением с откатом.

## Границы и ограничения

- Контракты API, роли, схема БД и версия PostgreSQL сохраняются. Выкладка отдельного VPS и тестового стенда Сбера остаётся на их текущих workflow.
- Docker локально не требуется. Локальные проверки — `.claude/verify.sh`, `bash -n` и сценарии обновлятора на заглушках. Контейнерные проверки идут в GitHub Actions или на авторизованном Linux-стенде.
- Для CI и серверной выкладки нужны действующие разрешения владельца. Конфигурация и учётные данные реального сервера остаются у владельца. Релизные артефакты и журнал не содержат секретов.

## Пре-мортем

- **Заглушки снова скрыли ошибку запуска.** Проверено на `c2c205a`: `checks.sh` всегда читает активный Compose, а заглушка принимает любой путь. Регрессия требует существующий файл и проверяет, что запущена версия с содержимым целевого релиза.
- **Проверили новый сайт отдельно и сломали Caddy целиком.** Фикстура содержит другой сайт и существующий импорт. Проверить сохранение и восстановление файлов, а также доступность прежнего сайта после отказа.
- **Скачивание прервалось, либо таймер и ручной запуск совпали.** Сравнить рабочую версию, активные файлы и команды изменения контейнеров до и после отказа. Ожидаемое поведение задано критериями выше.
- **Локальный verify зелёный, но релиз не публикуется.** Обязательные внешние проверки охватывают скачивание Caddy и сверку контрольной суммы, авторизацию GHCR, успешную публикацию, загрузку приватного релиза и первый запуск на чистом окружении.
