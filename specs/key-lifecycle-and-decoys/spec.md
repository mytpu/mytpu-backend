# Жизнь мастер-ключа: сроки по типу, заявки, самоперевыпуск, неактивность, ловушки с группами

Опирается на `specs/mcp-key-and-agent-safety` (часть А сделана: ключ v2, сети, приостановка, ловушки, `key_events`),
`specs/console-and-connectors` (API ключей консоли, журнал действий) и `specs/personal-data-for-agents` (часть А сделана:
классы полей и режимы выдачи по доверию). Решения владельца 2026-10-30/31; разбор практик и права — заметка
«Keys-and-PD-Law» в базе знаний команды.

## Зачем
Ключ должен жить ровно столько, сколько нужно его владельцу, обновляться без ручной возни и сам выключаться, когда
утёк или заброшен. Сейчас срок один (90 дней), заявок нет, перевыпуск — только руками администратора, ловушка лишь пишет
строку в базу, а неиспользуемый ключ живёт до конца срока.

## Принципы
- **Тот же секрет не продлевается.** Продление = перевыпуск с перекрытием (NIST SP 800-57, «криптопериод»): новый ключ,
  старый живёт переходный срок. Чтобы это не было «головной болью», клиент может перевыпустить ключ сам одним вызовом.
- **Срок зависит от того, что открывает ключ.** Публичные данные (расписание, сайт, инструкции) — долгие ключи интеграций
  с привязкой к сетям; личные данные студентов по мастер-ключу не выдаются вовсе — только по входу студента через ТПУ
  (спецификация 4, токены с тихим продлением, раз в 14–30 дней вход заново). Оценки — личные данные, не «нечувствительные».
- **Ловушка — датчик места.** Одна ловушка на место; сработала — место считается утёкшим вместе с настоящими ключами в нём.
- **Пороги и сроки — в `application.yml`, не литералами.**

## Критерии готовности (проверяемые)

**Типы и сроки**
- [x] Тип ключа: `person` (человек), `server` (интеграция с сетями), `demo` (показ, хакатон). Срок по умолчанию и предел — по типу
  из настроек: `person` 30 / 90 дней, `server` 90 / 365, `demo` 7 / 14. Ключ без сетей — не дольше 30 дней (как сейчас).
  Проверка: `issue-key --kind=demo` без `--days` → срок 7 дней; `--days=20` для `demo` → ошибка с пределом.
- [x] Администратор при выдаче и при одобрении заявки меняет срок в пределах типа; изменение пишет журнал действий.

**Заявки на ключ**
- [x] Таблица `key_requests`: кто, контакт, цель, нужные сервисы, тип, желаемый срок, статус (`new` / `approved` / `rejected`),
  кто и когда решил, причина отказа. Контакт — без лишних ПД (рабочая почта, без телефона).
- [x] `POST /admin/api/key-requests` (завести заявку), `GET` (список с фильтром), `POST …/{id}/approve` (тип, срок, сервисы,
  инструменты, лимиты — правила `KeyRules`; ответ — ключ один раз), `POST …/{id}/reject` (причина). Каждое — в журнале действий.

**Самоперевыпуск и напоминания**
- [x] `POST /mcp/key/rotate` с действующим ключом в заголовке → новый ключ (показывается один раз), старый живёт переходный срок
  (по умолчанию 24 ч, ≤ 7 сут); права, сети и тип — те же, срок — заново по типу. `demo` и ключ консоли → 403
  `rotate_not_allowed`; прежним ключом из переходного срока → 403 `rotate_current_key_only`; приостановленный, отозванный и
  ловушка отсекаются фильтром ключа (401, ловушка — как неверный ключ). Не чаще раза в сутки на ключ (429 и `Retry-After`).
  Событие `key.self_rotated`.
- [x] За 14 и за 3 дня до конца срока — событие `key.expiring` и оповещение (канал ниже); в консоли — список истекающих.

**Неактивность**
- [x] Ключ без вызовов 45 дней (порог в настройках) приостанавливается фоновой задачей раз в сутки: событие
  `key.inactive_suspended`, ответ клиенту 401 `key_suspended`, снять — администратор (`--resume` / консоль).
  Ключи консоли и ловушки — не трогаются.

**Ловушки**
- [x] У ловушки — место (`owner`) и группа: список настоящих ключей рядом (`decoy_group`, задаёт администратор).
  Срабатывание ловушки приостанавливает все ключи группы (событие `key.group_suspended` с id ловушки) и шлёт оповещение.
  Ответ на ловушку — как сейчас, неотличим от неверного ключа (статус, тело, заголовки); оповещение — асинхронно.
- [x] Оповещение: канал из настроек (вебхук; токен — файл-секрет), события `key.decoy_used`, `key.group_suspended`,
  `key.network_burst`, `key.expiring`. Сбой канала не мешает ответу клиенту и не теряет событие в `key_events`.
- [x] `docs/SECURITY.md`: где класть ловушки (репозиторий, CI, ноутбук, конфиг MCP-клиента), как вносить их отпечаток в
  `.gitleaksignore` с причиной, что делать при срабатывании.

**Инциденты и право**
- [x] `docs/SECURITY.md` §12: при утечке ПД — уведомление ТПУ (оператору) сразу, чтобы ТПУ уложился в 24 ч (первичное
  уведомление Роскомнадзора) и 72 ч (результаты расследования) по ч. 3.1 ст. 21 152-ФЗ; шаблон первичного уведомления
  (что случилось, причина, вред, меры, контакт); кто в команде за это отвечает.
- [x] `docs/SECURITY.md`: раздел «Вопросы к ТПУ» — договор поручения (ч. 3 ст. 6), уровень защищённости и модель угроз
  (ПП 1119, приказ ФСТЭК № 21), нужен ли ГОСТ-TLS (приказ ФСБ № 378), трансграничная передача при внешних агентах.

**Консоль (интерфейс — в части Б `console-and-connectors`)**
- [x] В план части Б консоли добавлены экраны: «Заявки на ключ» (список, одобрение со сроком), «События ключей»
  (ловушки, группы, новые подсети, приостановки, истекающие) — макеты FigCraft (делаются в шаге 8 части Б до кода).

## Не входит (non-goals)
- Самостоятельная подача заявок разработчиками с сайта — после спецификации 4 (вход ТПУ); до неё заявку заводит администратор.
- Продление того же секрета без перевыпуска.
- Привязка ключа к клиенту (DPoP, `private_key_jwt`), OAuth вместо ключей у внешних агентов — `mcp-key-and-agent-safety`, Б и В.
- Программа партнёров GitHub по поиску секретов, суточные квоты и поиск аномалий по объёму — потом.
- Режимы выдачи личных полей по доверию — сделано в `personal-data-for-agents` (А); здесь не меняются.

## Ограничения
- Безопасность: новый ключ — только в ответе одного запроса, в логах и журналах — префикс; вебхук оповещений — файл-секрет;
  в оповещении — id ключа, место, подсеть, без полного адреса и без ключа.
- Архитектура: всё в модуле `access` (+ контроллер в `admin`); новых `*Manager` нет; фоновые задачи — через `@Scheduled`
  и существующий `BackgroundWriter`.
- Память: без новых процессов; задачи — раз в сутки и по событию.

## Ответы на открытые вопросы (утверждено 2026-10-31)
1. Канал — вебхук; первым — Telegram-бот команды (адрес с токеном — файл-секрет).
2. Самоперевыпуск — для всех ключей, кроме `demo`, ключей консоли и ловушек.
3. Неактивность — 45 дней; отзыв ни разу не использованных — есть настройка, по умолчанию выключен.
- Исполнение: вся схема (тип `demo`, `key_requests`, группы ловушек, отметки перевыпуска и напоминаний) — одной миграцией
  V6 на шаге 1, чтобы не менять применённую миграцию на следующих шагах. Ловушка вне сроков по типу: по умолчанию и не
  дольше 365 дней (лежит на месте долго).
